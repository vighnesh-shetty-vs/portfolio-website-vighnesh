Case file 01 · Retail bank analytics

The bank could have seen the defaults coming.

Using only what a Czech retail bank knew on the day it approved each loan, a single warning sign predicted every default in its group. Here is how I built the warehouse to prove it, and the tests that stop the answer from being a data leak.

Data
PKDD'99 “Berka” bank data, 1993–1998 (real, anonymised)
Scale
4,500 accounts · 5,369 clients · 1.06M transactions · 682 loans
Stack
SQL · dbt · DuckDB · Power BI (DAX) · GitHub Actions
Role
Solo project · Oct 2026

TL;DR (30 seconds)

  • All 27 loans given to clients who had already been overdrawn defaulted, versus 7.5% for everyone else.
  • Account behaviour predicts default far better than the local economy: default rates barely move with district unemployment.
  • Every number comes from a warehouse with 55 tests in CI, including one that fails if any loan feature uses data from after the loan was granted.

01

The question

Overall, 11.1% of this bank's loans default, and they hold 15.1% of the exposure. The question a credit team actually cares about is narrower: at the moment of approval, was there anything in the client's own account history that should have stopped the loan?

That “at the moment of approval” is the whole problem. This dataset is famous for a trap: the guide that comes with it warns that “balance ever negative” separates good and bad loans perfectly if you ignore time, because a client who stops paying goes negative after the loan. A model built that way looks brilliant and is useless.

02

How I built it

  1. raw

  2. staging · 8

    Clean & translate

    Types, dates, Czech codes to English, ‘?’ to NULL

  3. intermediate · 2

    Point-in-time

    Loan features only from transactions before the grant date

  4. marts · 7

    Star schema

    Dims, facts and a month × district KPI table

  5. report

    Power BI

    3 pages, 21 DAX measures, row-level security

The staging layer does the unglamorous work: integer dates like 930105 become real dates, gender is decoded from Czech birth numbers (women have +50 on the month), and transaction codes such as PRIJEM or VYBER KARTOU are translated. Ten business questions are answered in SQL under analyses/, and the marts are exported for the Power BI report.

The Power BI project is saved as PBIP, so the model and report are plain text under version control. I checked the DAX against the SQL: 682 loans, 11.1% default rate, 103.3M CZK exposure and 195.6M CZK of December 1998 deposits match exactly.

All features use only transactions dated before each loan's grant date.

Account behaviour is the signal. An overdraft before the loan, or a balance that dipped below 5,000 CZK in the previous 90 days, separates risky borrowers far better than anything about where they live. Affordability matters too, but only in the worst quartile.

The report also surfaced a few things outside credit risk:

  • Longer loans default slightly more often (12% vs 8% for 12-month loans) and are much larger.
  • Card holders keep higher balances (gold-card accounts averaged 71.9k CZK in 1998 vs 33.4k without a card), yet cards carried only about 1% of outgoing money. Cash was still 75%.
  • Cash demand peaks in January, June and December, at 25–49% above the monthly average: useful for branch and ATM cash planning.
  • No loans went to account owners aged 65+ (675 of them). That is either a lending policy or a gap worth asking about.

04

Why you can trust the numbers: 55 tests

Daily balance reconciliation

Each day's balance must equal the previous day's plus that day's net flow. It exposed two quirks in the source: intra-day order isn't recorded, and interest is rounded differently. 763,838 account-days reconcile exactly; 46,430 (5.7%) are off by at most 0.20 CZK. The test now allows any intra-day order and a 0.50 CZK tolerance.

No target leakage

A test fails the build if any loan feature uses a transaction on or after the grant date. This is what keeps the headline finding honest.

Keys and codes

unique, not_null and relationships tests on every key, plus accepted values for every decoded code.

Business rules

Loan amount = monthly payment × duration (true for all 682 loans); no transaction is dated before its account opened.

All 55 run on every push in GitHub Actions, and the dbt docs are published from CI.

05

The Power BI report

Star schema of 6 tables with a marked date table; 21 measures including latest-month semi-additive balances, SAMEPERIODLASTYEAR and DIVIDE-safe ratios; an RLS role (Regional Manager – Prague); and an explicit en-US parse culture so it loads on a French Windows setup.

06

What I would tell the bank

  1. 1Make overdraft history and a 90-day low-balance flag hard checks at approval. Both are already in the bank's own data on the day of the decision.
  2. 2Review the affordability threshold for the least affordable quartile, where defaults are roughly 3× the rest.
  3. 3Don't spend effort on district-level economic adjustments for retail loans; behaviour carries the signal.
  4. 4Ask whether excluding customers aged 65+ from lending is deliberate policy, and plan branch cash for the January, June and December peaks.

07

Limitations

  • Old data, one bank. 1993–1998 in one country; the patterns need re-checking on current data before anyone acts on them.
  • Small group. The 100% default rate rests on 27 loans. It is a strong signal, not a precise estimate.
  • Only approved loans. The data has no rejected applications, so it can't say how the flags would behave on clients the bank already turned away.
  • Association, not cause. These are descriptive rates. A production scorecard would need a proper model, validation and monitoring (see my credit scorecard project).
